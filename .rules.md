
# .rules
# =========================================================
# AGILE-V GLOBAL PROJECT RULES
# =========================================================

version: 1.0.0

# =========================================================
# GENERAL
# =========================================================

- Always analyse the entire project before making changes.
- Never assume requirements without sufficient evidence.
- Think before generating code.
- Prioritise maintainability over shortcuts.
- Prefer production-ready solutions.
- Follow Agile + Scrum principles.
- Keep documentation synchronised with implementation.
- Never leave broken builds.
- Never intentionally introduce technical debt.
- Every change must have a clear purpose.

# =========================================================
# DOCUMENTATION
# =========================================================

- The ".agile-v" folder is the single source of truth.
- Update documentation whenever implementation changes.
- Never leave outdated documentation.
- Cross-reference related documents.
- Record architectural decisions.
- Record requirement changes.
- Record breaking changes.
- Record completed work.
- Record pending work.
- Record blockers.
- Maintain a changelog.

# =========================================================
# PROJECT ANALYSIS
# =========================================================

Before implementing anything:

- Analyse the repository.
- Understand existing architecture.
- Review dependencies.
- Review configuration.
- Review folder structure.
- Review coding conventions.
- Review business requirements.
- Review existing documentation.
- Review open issues.
- Identify risks.

# =========================================================
# ARCHITECTURE
# =========================================================

Always follow:

- SOLID
- DRY
- KISS
- YAGNI
- Clean Architecture
- Domain Driven Design
- Separation of Concerns
- Dependency Injection
- Single Responsibility
- Composition over Inheritance

Never create unnecessary abstractions.

# =========================================================
# CODE QUALITY
# =========================================================

Every implementation must:

- Be readable.
- Be modular.
- Be reusable.
- Be maintainable.
- Be scalable.
- Include meaningful naming.
- Avoid duplicated logic.
- Avoid dead code.
- Avoid magic numbers.
- Avoid hardcoded secrets.
- Include proper error handling.

# =========================================================
# NAMING
# =========================================================

Use consistent naming.

Variables:
camelCase

Functions:
camelCase

Classes:
PascalCase

Interfaces:
PascalCase

Enums:
PascalCase

Files:
Use the project convention consistently.

Folders:
lowercase-with-hyphen or project convention.

# =========================================================
# SECURITY
# =========================================================

Never:

- Hardcode credentials.
- Store secrets in source code.
- Disable authentication.
- Disable authorisation.
- Disable validation.

Always:

- Validate user input.
- Sanitize input.
- Escape output.
- Encrypt sensitive data.
- Hash passwords.
- Use environment variables.
- Follow OWASP Top 10.
- Use secure defaults.

# =========================================================
# DATABASE
# =========================================================

Always:

- Normalise schema.
- Add indexes where required.
- Use migrations.
- Avoid redundant columns.
- Define foreign keys.
- Prevent orphan records.

Never:

- Delete production data accidentally.
- Use SELECT * unless appropriate.

# =========================================================
# API
# =========================================================

Every endpoint must:

- Validate requests.
- Return meaningful responses.
- Return proper status codes.
- Handle errors consistently.
- Support pagination where appropriate.
- Support filtering.
- Support sorting.
- Be documented.

# =========================================================
# FRONTEND
# =========================================================

Always:

- Build reusable components.
- Follow the design system.
- Support responsive layouts.
- Support accessibility.
- Optimise performance.
- Avoid unnecessary renders.
- Optimise assets.

Never:

- Duplicate components.
- Hardcode UI values repeatedly.

# =========================================================
# BACKEND
# =========================================================

Always:

- Separate business logic.
- Separate data access.
- Separate routing.
- Use services where appropriate.
- Keep controllers lightweight.

Never:

- Mix business logic into controllers.
- Duplicate validation.

# =========================================================
# TESTING
# =========================================================

Before completion:

- Verify functionality.
- Check edge cases.
- Verify error handling.
- Verify validation.
- Verify permissions.
- Verify performance where applicable.

# =========================================================
# PERFORMANCE
# =========================================================

Optimise:

- Queries
- API calls
- Rendering
- Caching
- Asset loading
- Bundle size
- Memory usage

Avoid premature optimisation.

# =========================================================
# GIT
# =========================================================

Use meaningful commits.

Prefer:

feat:
fix:
refactor:
docs:
style:
test:
perf:
chore:

Keep commits focused.

# =========================================================
# AGILE
# =========================================================

Every feature should include:

- Requirement
- User Story
- Acceptance Criteria
- Tasks
- Dependencies
- Risks
- Testing
- Documentation

# =========================================================
# IMPLEMENTATION WORKFLOW
# =========================================================

For every task:

1. Analyse requirements.
2. Review existing code.
3. Identify impacted files.
4. Design the solution.
5. Implement changes.
6. Update documentation.
7. Verify functionality.
8. Update progress.
9. Record decisions.
10. Record changelog.

# =========================================================
# CHANGE MANAGEMENT
# =========================================================

Whenever code changes:

Update:

- Requirements
- Architecture
- API documentation
- Database documentation
- UI documentation
- Testing documentation
- Sprint progress
- Changelog
- Release notes

# =========================================================
# QUALITY GATE
# =========================================================

Before considering work complete, ensure:

✓ No compilation errors.
✓ No obvious bugs.
✓ Documentation updated.
✓ Requirements satisfied.
✓ Acceptance criteria met.
✓ Architecture remains consistent.
✓ No duplicated logic.
✓ No unused code.
✓ Security reviewed.
✓ Performance acceptable.

# =========================================================
# FINAL RULE
# =========================================================

Never optimise for speed at the expense of quality.

Always deliver production-ready, maintainable, secure, scalable, and well-documented solutions.

Treat every project as if it will be maintained by a large engineering team for many years.
